### Version and directory rules

- A newer version may replace an older version in the same scope; an equal
  version may repair/reinstall; an older version is rejected before writes.
- Installed versions are not trusted from `DisplayVersion` alone. The policy
  cross-checks the strict three-component version against the executable's
  Windows numeric version, the scope marker, the registered installation path
  and Inno's previous path. A present marker version must agree too. Legacy
  Scope-only markers remain supported when the other checks agree. Native
  registry reads distinguish absence from access failure; both views are checked.
- Numeric comparison includes multi-digit components and unsigned 16-bit Windows
  version words. A test exposed Inno 6.7.1's signed packed-version ordering for
  major versions at/above 32768; the policy now handles that boundary explicitly.
- `UsePreviousAppDir=yes` continues native previous-path reuse. To deliberately
  change the directory of an installed scope, uninstall that copy with data
  preserved, then install into the new empty directory. An in-place attempt to
  select another directory is rejected. This avoids leaving an old executable
  and uninstaller under the same stable identity; no silent move/deletion occurs.
- Repair requires a verifiable main executable and installation identity.
  Ancillary file repair is tested. A missing/corrupt executable or contradictory
  registration fails closed and requires uninstall/reinstall with data preserved.
- New roots must be empty and separate from existing installation roots. Equal
  and nested destinations, ambiguous paths, reparse points and inaccessible
  paths are rejected. Handle-based normalization resolves short-name/drive
  aliases; an unavailable-drive loop found in review was fixed and tested.
- Local mode now consumes exact generated per-file entries with the same
  destination checks as Online mode. `ValidateOnlinePayload` retains its old
  validation responsibility through the canonical destination validator.

The separate CurrentUser/AllUsers AppIds, registration and shell folders remain
in use. Shortcut replacement validates the target. After a successful install,
only this scope's owned obsolete English/Russian links are removed; unchecking
the desktop task removes its owned desktop link. A foreign/unreadable shortcut
blocks installation. New Setup and Uninstall processes share a global lifetime
lock, preventing overlapping installer state changes. This does not close or
detect running JobTracker instances; the manual-close workflow remains stage 11.

### Shared-data compatibility policy

Live `src/app/App.cpp` still names the application `JobTracker` and
`src/storage/StoragePaths.cpp` still uses
`QStandardPaths::AppLocalDataLocation/Data/{database.sqlite,Resumes}`.
Installation scope does not isolate this per-account data.

Only **equal release versions** may coexist across installation scopes.
Current-user Setup checks machine installations. All-users Setup checks regular
Windows profiles from `ProfileList` and loaded user hives. An unloaded or
unreadable profile blocks the operation; the user must sign in to that profile
and keep its session open, or choose current-user installation. No offline hive
is loaded and no other account's data or registration is modified. This strict
policy can block all-users installation on multi-user systems until every
profile is inspectable. The host's read-only all-users audit actually reached
and passed the expected `InstallProfileUnavailable` rejection.

For two equal-version installations, the supported update sequence is: uninstall
one copy preserving data, upgrade the remaining copy, then install the other at
the same new version. Setup never opens SQLite, runs migrations, launches the
application or deletes personal data. Equal versions are a conservative
installer gate, not proof of concurrent application/database safety.

## Remaining blockers and risks

No essential stage-10 implementation blocker remains. `DONE` records the
implemented, locally compiled/tested policy; it does not certify release readiness.

Real AllUsers/UAC, simultaneous installations/uninstall isolation, multi-session
profile visibility/ACL behavior and GUI/clean-machine acceptance remain required.
The strict unloaded-profile block is intentional and may require an operator to
resolve stale profiles or choose current-user mode. No automatic profile loading,
account impersonation or unsafe bypass is provided.

The installer does not track a lifetime database schema/version history. Complete
uninstall followed by an old installer, manually copied executables, older
installer/uninstaller versions, or external registry/filesystem edits can bypass
these new gates. Old uninstallers do not use the lifecycle lock. Same-version
coexistence does not establish safe simultaneous application execution. Preserve
backups and do not open newer data with older binaries; no migration compatibility
claim is made. Application-running detection is deliberately left to stage 11.

The unchanged public archive, MSVC pin, graphics/DXC limitations and distributor
license/release checks remain as documented by earlier stages. No Git writes,
publishing, signing, personal-data deletion or machine-runtime installation occurred.
