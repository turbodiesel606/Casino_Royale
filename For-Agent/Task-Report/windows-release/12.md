### Data identity and policy

- `src/app/App.cpp` sets application name `JobTracker`, with no organization
  override. Qt 6.10.3's normal Windows `AppLocalDataLocation` is the account's
  Local AppData known folder plus `JobTracker`; `StoragePaths.cpp` adds `Data`,
  `database.sqlite` and `Resumes/`. Thus the normal path is
  `%LOCALAPPDATA%\JobTracker\Data`. The uninstaller resolves `{localappdata}`
  through Windows, not an environment variable or a command-line path override.
- Source search found no `QSettings`, QML `Settings`, or other organization-name
  override. The optional deletion target is the exact `JobTracker` application
  folder, including SQLite sidecars, imported CVs and any other contents. The
  confirmation names that exact folder and warns that deletion is permanent.
- The initial CurrentUser HKCU record must identify this exact installation.
  AllUsers and **every elevated uninstall preserve data**, including same-account
  elevation: the original interactive account is not reliably recoverable.
  No other account's folders or profile registry hives are enumerated for cleanup.
- Data deletion is reachable only from `usDone`, after an interactive Yes. Native
  `usDone` is not itself proof of complete removal: an observed no-restart callback,
  the entire program directory being absent, both localized scoped shortcuts
  being absent, and no CurrentUser/AllUsers registrations in either registry view
  are also required. Unknown program leftovers conservatively block cleanup.
- Presence of even a malformed/old installation record blocks deletion;
  unreadable state fails closed. Completion/coexistence checks repeat after
  consent while the existing global installer lifecycle lock remains held.
  Remaining/uncertain installations receive an explanatory localized message.
- Silent uninstall never authorizes deletion, including an unrecognized
  `/DELETEPERSONALDATA=yes` argument. No/closing the prompt, pre-completion
  cancellation, Setup errors/rollback and deinitialization cannot initiate cleanup.
- Cleanup pins every ancestor without delete sharing, opens children without
  following reparse points, verifies actual handle paths and token SID ownership,
  rejects file hardlinks, and opens every file exclusively before mutation.
  Native enumeration distinguishes a complete listing from an error. Locked,
  read-only, inaccessible, ambiguous/aliased or redirected paths fail preflight
  without deleting any file. Bounds: 240-character paths, depth 32, 8192 handles.
- Only already-open validated handles receive bottom-up deletion dispositions.
  No recursive pathname deletion, ownership/ACL modification, process termination
  or reboot-scheduled personal-data deletion occurs. Local AppData and siblings
  are never deletion targets.
- Cleanup is not transactional. A late Windows error, crash or concurrent new
  entry can leave a partially removed, explicitly confirmed tree. Cleanup stops
  on the first failure, preserves remaining objects and explains the limitation.
  No restoration guarantee is made. Unregistered/manual copies cannot be
  exhaustively discovered; their users are explicitly told to keep shared data.
