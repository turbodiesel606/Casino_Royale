## Qt licensing analysis

**LGPLv3 (the applicable Qt route).** The exact Windows Qt 6.9.1 kit SBOM lists LGPL-3.0-only as an alternative for the directly and transitively needed modules above. Qt's own 6.9 licensing page allows LGPLv3 applications if its terms are met and separately lists GPL-only modules. LGPLv3 §4 allows application code under your own terms if you prominently identify the library, include **both LGPLv3 and GPLv3** texts (LGPLv3 incorporates GPLv3), preserve copyright notices, use a suitable shared-library mechanism or provide relinkable application code, and do not restrict modifying/reverse-engineering the LGPL portion for debugging. Conveyed Qt binaries also require Qt's corresponding source availability, including your Qt changes, following GPLv3 §6 and Qt's explicit guidance. [Qt 6.9 licensing](https://doc.qt.io/archives/qt-6.9/licensing.html); [LGPLv3 §4](https://www.gnu.org/licenses/lgpl-3.0.html); [GPLv3 §6](https://www.gnu.org/licenses/gpl-3.0.html); [Qt obligations](https://www.qt.io/development/open-source-lgpl-obligations).

**LGPLv2.1.** Do not treat it as interchangeable with LGPLv3. The inspected Qt 6.9.1 module SBOM offers **LGPLv3**, not LGPLv2.1, for these Qt modules. LGPLv2.1 may matter to a separate third-party library in a future package (or a different Qt product such as WebEngine, which JobTracker does not use). Its §6 also permits proprietary work with suitable shared-library linking, license notices, and user relinking, but its installation-information wording differs. Audit that actual library and its exact terms if introduced. [LGPLv2.1 §6](https://www.gnu.org/licenses/old-licenses/lgpl-2.1.html); [Qt WebEngine licensing, for the distinct case](https://doc.qt.io/qt-6/qtwebengine-licensing.html).

**GPL option.** A GPL-only Qt module, such as the Virtual Keyboard or Quick 3D files currently in the Debug directory, is not covered by the Qt LGPL choice. Qt says use of GPL-only framework libraries requires the application/device to be under GPL too. Merely copying unused GPL-only files creates a distribution/license issue that should be eliminated rather than argued away. A controlled package that excludes them is the practical route. [Qt 6.9 licensing, GPL-only list](https://doc.qt.io/archives/qt-6.9/licensing.html); [Qt obligations, “Developing with GPL”](https://www.qt.io/development/open-source-lgpl-obligations).

**Commercial Qt.** It provides separate commercial terms, access to modules that lack LGPL options and easier static/restricted-device distribution. It is a developer-license subscription option, not a required fee simply because JobTracker is paid. Do not mix a commercial Qt kit and community terms casually: Qt's [commercial FAQ](https://www.qt.io/faq/qt-commercial-licensing) describes a team choice between complying with community terms and buying commercial developer licenses, and warns that later migration can require Qt's assistance. No decision here relies on buying it.

**Source distinction.** JobTracker-owned C++/QML may remain closed. The exact Qt source corresponding to shipped Qt binaries, including modifications to Qt, must be made available by a compliant method; source for a separate LGPL library must similarly be provided under that library's terms. A mere link to Qt's public download is insufficient according to Qt's [open-source obligations](https://www.qt.io/development/download-open-source): a written offer/instructions must remain under **your control**. Providing the exact archived sources and build configuration yourself is the clearest approach. The actual LGPL does not generally require sending Qt changes *upstream* to the Qt Project; it requires licensing/providing covered modifications to recipients. Qt's marketing shorthand about contributing changes should not replace the license text. Legal counsel recommended on any Qt modifications.

## Current linking and library replacement

The existing executable's PE import table names separate Qt Debug DLLs. The root CMake uses Qt import targets from the installed shared MSVC kit; there is no `-static` Qt build or static Qt archive linkage in the inspected build. Embedding JobTracker QML into the executable does **not** turn the Qt libraries into static libraries. A future Release or Linux binary must be verified independently.

**Windows practical route:** ship `JobTrackerApp.exe`, matching replaceable Qt 6.9.x Release DLLs, Qt QML imports/plugins, `platforms/qwindows.dll`, `sqldrivers/qsqlite.dll`, and the proper MSVC Release runtime provision. Ordinary DLL loading from an accessible application directory can satisfy the LGPLv3 shared-library mechanism **if** a user can replace a Qt DLL with an interface-compatible modified one and run the application. A DLL being physically separate is necessary but is not alone proof: test that the installer, launcher, updater, signature check, ACLs, or license code does not reject the modified DLL. Allow reverse engineering needed to debug Qt modifications. The developer need not guarantee arbitrary ABI-incompatible DLLs work. [LGPLv3 §4(d)(1)](https://www.gnu.org/licenses/lgpl-3.0.html); [Qt obligations](https://www.qt.io/development/open-source-lgpl-obligations); [Qt 6.9 Windows deployment](https://doc.qt.io/archives/qt-6.9/windows-deployment.html).

**Linux practical route:** use ELF shared Qt `.so` libraries and QML/SQL/platform plugins that the user can replace in a documented deployment location, or use compatible system/runtime Qt libraries. Verify `RPATH`/`RUNPATH`, plugin search paths and loader behavior. A read-only AppImage can normally be extracted and repacked by its user, but that must be tested and documented; a Flatpak/runtime or immutable store package needs its own replacement assessment. An updater may overwrite a modified library, but it should not permanently prohibit reinstallation or running a modified interface-compatible Qt. Installer privileges and code signing are not inherently forbidden; an unbypassable hash/signature gate on LGPL Qt, or DRM/anti-tampering that prevents execution with modified Qt, may violate §4 and, in a covered “User Product,” installation-information rules. [LGPLv3 §4(e), GPLv3 §6](https://www.gnu.org/licenses/lgpl-3.0.html); [AppImage concepts](https://docs.appimage.org/introduction/concepts.html); [Flatpak dependencies](https://docs.flatpak.org/en/latest/dependencies.html).

**Static Qt:** LGPLv3 §4(d)(0) calls for Minimal Corresponding Source plus Corresponding Application Code in a form permitting recipients to recombine/relink with modified Qt, and §4(e) may require installation information. That can mean linkable object files and instructions without publishing proprietary source, but it is operationally complex for QML/plugins and needs careful legal review. Dynamic linking is the concrete recommendation. [LGPLv3 §4](https://www.gnu.org/licenses/lgpl-3.0.html); [Qt obligations, static-link warning](https://www.qt.io/development/open-source-lgpl-obligations); [Qt deployment, static vs shared](https://doc.qt.io/qt-6/deployment.html).

The observed Windows tree has `tls/qcertonlybackendd.dll` and `tls/qschannelbackendd.dll`, no `qopensslbackendd.dll` or OpenSSL DLLs. OpenSSL must **not** be invented as a current dependency. If a future package uses OpenSSL, audit its exact version, license, notices and export considerations; Qt's [deployment licensing section](https://doc.qt.io/qt-6/deployment.html) calls this out. The same rule applies to optional image formats and their bundled TIFF/WebP code. Qt's installed SBOM is more exact than a generic list of everything the Qt SDK contains.

For Windows, the Microsoft C++ **Release** runtime can be redistributed only according to the Visual Studio license/REDIST list by a validly licensed Visual Studio user. The existing `MSVCP140D.dll`, `VCRUNTIME140D.dll`, `VCRUNTIME140_1D.dll`, `ucrtbased.dll` imports are Debug and are not a commercial release artifact. Use the matching official x64 redistributable and check the toolchain license. Linux has not been built or inspected on this host. Its package may depend on system `glibc`, `libstdc++`, `libgcc_s`, XCB/Wayland and graphics libraries, and the chosen Qt kit may compile in or load further code. These are **conditional**, not confirmed shipped dependencies. Audit the Linux ELF imports and deployed tree before release. ## EULA coexistence

You can license JobTracker-owned C++/QML under your proprietary EULA and redistribute separate Qt libraries under LGPLv3. The EULA should say third-party components retain their own licenses and that nothing in the EULA restricts the rights to copy, inspect, modify, replace or debug LGPL-covered components. Avoid blanket clauses forbidding *all* reverse engineering, *all* modifications, *all* redistribution, or removal/replacement of *all* program components when they would be applied to Qt. A prohibition on bypassing JobTracker's own paid-feature licensing can be drafted separately, but must not prevent use of a modified compatible Qt library. Place EULA terms at product/installer level and LGPL notices alongside them. [LGPLv3 §4 combined works](https://www.gnu.org/licenses/lgpl-3.0.html); [Qt obligations, nonrestriction](https://www.qt.io/development/open-source-lgpl-obligations). Legal counsel recommended for the wording and local consumer law.

## License keys and recommended offline architecture

An online activation server is **not required by Qt or by a perpetual desktop license**. A plain `XXXX-...` key can be a randomly generated entitlement looked up online, but without a server or embedded list it is not self-verifying. A signed license file is better for an offline local-first application:

```text
Verified purchase / manual order review
          ↓
payload: product, edition, order ID, seats, maximum major version,
         optional update entitlement, issue date, optional customer name
          ↓
sign canonical payload with developer-held private key
          ↓
deliver license.json + signature (or one signed file)
          ↓
JobTracker verifies signature using embedded public key, then applies entitlement
```

Use a standard digital signature (for example Ed25519 per [RFC 8032](https://www.rfc-editor.org/rfc/rfc8032)); keep the private key out of the app, source repository and customer package. Canonicalize the payload, version the license format, minimize personal data, and support key rotation/reissue and refund handling. A small fulfillment script or manual signing can run only when a purchase occurs; the desktop app needs no permanent server. A reseller's key-generation API is another route but may require online activation; distinguish provider keys from an independently verifiable offline signature.

Online activation enables device limits/revocation and easier refund enforcement, at the cost of hosting, outages, privacy notices and customer support. Account-based licensing adds password/reset infrastructure and makes an offline job tracker less attractive. Store-managed entitlement reduces custom billing but ties customers to the store. None should validate the cryptographic hash of Qt DLLs as a condition for the user's LGPL replacement right. Offline licensing cannot perfectly stop piracy; it can establish a reasonable purchase entitlement without imposing always-on service.

## Installers, code signing and updates

**Windows packaging.** For direct distribution, a portable ZIP or **NSIS** installer is a low-overhead first route. [NSIS's official license](https://nsis.sourceforge.io/Docs/AppendixI.html) expressly permits commercial applications under its conditions. Inno Setup is easy technically, but its current [commercial-license page](https://jrsoftware.org/isorder.php) requests a purchased license from commercial users above its revenue threshold, while saying purchase is *not strictly required*. Thus it is not the cleanest recommendation for a “no paid license” target. [WiX's current maintenance-fee rules](https://docs.firegiant.com/wix/osmf/) can require sponsorship for organizations above $10,000 annual revenue; check version/terms before choosing it. MSIX requires package signing and its immutable package/Store behavior needs a demonstrated LGPL replacement route. Each installer must contain the same notices/source-access material as the extracted application. [MSIX signing](https://learn.microsoft.com/en-us/windows/msix/package/signing-package-overview); [Qt Windows deployment](https://doc.qt.io/archives/qt-6.9/windows-deployment.html).

**Linux packaging.** First validate the current Qt deploy output in a normal directory, then choose a `deb`/`rpm` with shared Qt/runtime dependencies or an AppImage with controlled bundled Qt `.so` files. [`linuxdeploy`](https://github.com/linuxdeploy/linuxdeploy) is an MIT-licensed packaging tool, not a JobTracker runtime dependency; commercial use of the tool does not itself impose Qt Commercial. Inspect the licenses of its plugins and of every library it copies into a release. AppImage is portable but its read-only image requires documented extract/repack or equivalent replacement testing. Flatpak has managed runtimes and updates but sandbox/immutability and library substitution warrant separate review. Distribution-specific policies and the exact Qt/plugin tree matter more than the extension of the package. [AppImage concepts](https://docs.appimage.org/introduction/concepts.html); [Flatpak dependencies](https://docs.flatpak.org/en/latest/dependencies.html); [Qt deployment](https://doc.qt.io/qt-6/deployment.html).

**Code signing.** An ordinary direct-download EXE/ZIP does not need an Authenticode signature as a universal legal condition for sale, but unsigned files face SmartScreen/user trust friction. Sign the installer and application for professional distribution when viable, and timestamp signatures. Microsoft says **EV no longer bypasses SmartScreen**, so paying extra for EV solely for that purpose is not justified. A signed installer need not lock Qt DLLs after installation. MSIX requires a trusted signature for normal deployment; Microsoft signs Store MSIX, while Store-submitted MSI/EXE signing remains the publisher's responsibility. A certificate or signing service may carry recurring cost and is a business/security choice, not a Qt fee. Linux `deb`/`rpm` repositories typically use package/repository signatures; direct AppImage releases benefit from published checksums/signatures. [Microsoft SmartScreen guidance](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/smartscreen-reputation); [code-signing options](https://learn.microsoft.com/en-us/windows/apps/package-and-deploy/code-signing-options); [MSIX signing](https://learn.microsoft.com/en-us/windows/msix/package/signing-package-overview).

**Updates.** Start with manual signed downloads and a release page; publish version, release notes, hash, and matching notices/source package. Public [GitHub Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases) can host binaries, but anyone with repository read access can download them, so they are a delivery channel, not a paid-access gate. Private hosting/processor delivery can gate downloads but adds account/hosting work. A built-in updater or update API can later automate version checks and authenticated downloads; it should not require a subscription to run a perpetual version, and must not make modified LGPL Qt impossible to use. Third-party update services add fees and their own redistribution/licenses. A 1.x perpetual license can receive all 1.x updates; 2.x can be a paid upgrade, or a signed `updates_until` entitlement can limit new releases while old versions keep running.

## Example Windows release layout

This is a **structure**, not a verified exact file list. Use the final Release binary and Qt SBOM to generate the real manifest. Exact Qt QML subdirectories/styles are platform-dependent.

```text
JobTracker-1.x-windows-x64/
  JobTrackerApp.exe
  Qt6Core.dll
  Qt6Gui.dll
  Qt6Qml.dll
  Qt6Quick.dll
  Qt6Sql.dll
  ...other required LGPL-eligible Qt Release DLLs...
  platforms/qwindows.dll
  sqldrivers/qsqlite.dll
  qml/QtQuick/...                 # only required Qt QML modules/styles
  LICENSE.txt                    # JobTracker EULA; third-party carve-out
  THIRD_PARTY_LICENSES.txt       # Qt 6.9.1, components, copyrights, other notices
  licenses/LGPL-3.0.txt
  licenses/GPL-3.0.txt
  licenses/...                   # exact permissive licenses for shipped code
  QT_SOURCE_AND_REPLACEMENT.txt  # your controlled source location/offer and steps
  RELEASE_MANIFEST.txt           # versions, paths, hashes, license IDs
  README.txt
```

The release should not contain `Qt6VirtualKeyboard.dll`, Qt Quick 3D files, `qmltooling`, Debug-suffixed Qt DLLs, test binaries, Debug CRT files, unused SQL drivers, or optional plugin families without a specific reason and license review. `windeployqt` is suitable to discover/copy dependencies, and commercial applications may use it with LGPL Qt; **its output is not a license clearance**. Audit each copied library/plugin/QML file, and stage only the approved set. The presence of `platforms/qwindows.dll`, `imageformats/*`, `sqldrivers/*` or `styles/*` is a separate license question for each shipped plugin. [Qt 6.9 Windows deployment, `windeployqt` and plugin sections](https://doc.qt.io/archives/qt-6.9/windows-deployment.html); [Qt SBOM](https://doc.qt.io/qt-6/sbom.html).

## Recommended commercial architecture and minimal path to first paid release

**Legal/licensing requirements:** retain proprietary ownership of JobTracker; use only LGPL-eligible, dynamically linked Qt runtime files; deliver prominent notices, LGPLv3/GPLv3 texts and Qt source availability under your control; preserve modified-library replacement and relevant reverse-engineering rights; satisfy each shipped third-party notice; honor actual MSVC redistributable terms. Do not ship GPL-only Qt extras under an LGPL-only proprietary model. [Qt obligations](https://www.qt.io/development/open-source-lgpl-obligations); [LGPLv3 §4](https://www.gnu.org/licenses/lgpl-3.0.html); [MSVC redistribution](https://learn.microsoft.com/en-us/cpp/windows/redistributing-visual-cpp-files?view=msvc-170).

**Business recommendation:** sell a perpetual 1.x license with optional paid major upgrade, use an offline signed entitlement, and start with direct Windows Release ZIP/NSIS plus manual updates. Test Lemon Squeezy and Gumroad seller onboarding/payout from Azerbaijan; compare Paddle after explicit seller confirmation. Add Linux only after a separate native package audit. Code signing is highly desirable but optional for the first direct ZIP; do not promise it avoids all SmartScreen warnings. Obtain counsel/accountant review before publication, without treating Qt Commercial as the default answer.

Concrete sequence:

1. Confirm ownership/provenance of all JobTracker C++/QML, and select a proprietary EULA with an explicit third-party LGPL carve-out. Legal counsel recommended.
2. Build an isolated **Release** binary and an allowlisted runtime stage; inspect direct/transitive DLLs, QML imports, plugins, optional graphics/runtime dependencies and exact SPDX identities. Exclude GPL-only Qt extras and Debug files.
3. Generate `THIRD_PARTY_LICENSES`, full LGPLv3/GPLv3 texts, Qt 6.9.1 corresponding-source archive or controlled fulfillment offer, Qt build/patch metadata, hashes and replacement instructions. Keep this per release.
4. Test installation, offline launch, SQLite operations, file dialogs, fonts/graphics and Qt DLL substitution on a clean Windows machine. Repeat independently on Linux before Linux sales.
5. Package via ZIP or NSIS, preserving separate Qt files and all notices. Add a code signature when available; do not adopt MSIX/Store until replacement behavior has been proven.
6. Implement a simple offline signed license with major-version entitlement and optional trial; no permanent activation server required. Keep its checks independent of Qt DLL identity.
7. Verify merchant onboarding and payout using the developer's actual Azerbaijan legal/banking details; publish clear price, updates, support and refund terms. Obtain local tax advice.
8. Publish signed or hashed installers, release notes, reproducible file/license manifests and matching Qt source/notice materials for each version. Retain older release materials and a manual download path for entitled customers.
