## Source-established R0 findings

### F001 — Partial cursor results can reach startup file recovery

**Consequence and condition.** A cursor that fails during iteration differs from a query that fails to execute. `CvRepository::findAll` returns the rows assembled so far after `recordDatasetReadError` logs the cursor error. Bootstrap immediately passes those rows to `CvManagedFileStore::reconcile`. If a referenced CV is among the missing rows, an ordinary completed file may be quarantined. A retained `.delete` file for an omitted row may be removed instead of restored. If recovery returns and a window is created, bootstrap can then log successful startup. The jobs/technology and company readers also permit partial results. The conditional consequences follow from R0 source. No incomplete read, file loss or successful startup was observed in this audit.

**Evidence.** `src/storage/SqlQuery.cpp:55–61`, `src/cvs/CvRepository.cpp:74–93,103–127`, `src/app/AppBootstrap.cpp:15–22,164–176`, `src/cvs/CvManagedFileStore.cpp:410–437,464–483`, `src/jobs/JobRepository.cpp:135–146,161–174`, `src/directory/CompanyRepository.cpp:58–68`. The expected startup event includes successful required loading in `Requirements/JobTracker_Logging_Events_Updated.md:165–167`.

**Disposition.** Defer changes at the cursor-success and startup-recovery boundary. Stage 2 may use an isolated fixture if a reliable failure can be reached through existing interfaces. Record any missing injection coverage. Never exercise recovery against personal records. This is distinct from the catch-path cleanup in R009.

### F002 — Checked CV counts can miss a relationship change

**Consequence and condition.** Select only active CV A with one linked application. Replace that application's CV with another existing active CV B which is not checked, with the ordinary updated-time sort. The previous link is removed, but the explicit checked-count notification is conditional on the destination being selected. The earlier removal emits link-count model roles. Changed linkage alone does not change the checked-ID set. The counts read from the controller can therefore differ from the values still displayed by a binding to `checkedCvsChanged`. The active-removal dialog uses those counts to describe archiving versus permanent deletion.

**Evidence.** `src/app/AppBootstrap.cpp:67–74`, `src/cvs/CvLibraryController.cpp:63–86,186–195,753–771`, `src/cvs/CvListModel.cpp:137–166`, `src/common/BulkIdSelectionTracker.cpp:23–32,158–172`, `src/cvs/CvLibraryController.hpp:65–70`, `qml/pages/CvLibraryPage.qml:168–174`.

**Disposition.** In stage 2 compare getter values, emitted notifications and dialog text using a disposable database. Opening the confirmation is sufficient. Do not perform a deletion to demonstrate a presentation discrepancy. R001/R003 must preserve this distinction. Native display of the stale value remains unverified.

### F003 — Log retention can use a size from a different file

**Consequence and condition.** If a Linux process renames the open segment and installs a smaller ordinary file at that name, `prune` can use the old handle's size for the newly scanned entry with the same segment number. Once the cached threshold triggers pruning, a closed older segment could be removed even while the on-disk directory is within its 50 MiB budget. Directory identity, name and a closed candidate's size are checked. They do not establish identity between the active handle and the current active path.

**Evidence.** `src/logging/LogFileWriter.cpp:35–59,137–170`. Existing `LogWriterTest::rechecksPhysicalUsageBeforeDeleting` and `replacedLogDirectoryCannotRedirectPruning` exercise different conditions. The prior review named this scenario. Its source was rechecked at R0.

**Disposition.** Retention behavior is outside the refactoring plan. If checked at a later Linux stage, use an isolated temporary log directory. No active-file replacement or deletion was observed here.

### F004 — The job-deletion failure total can disagree with the UI

**Consequence and condition.** In one batch with a missing job, a separate failing SQL delete, and a committed deletion, `BatchFacts::observe` logs the state mismatch without incrementing `failedJobs_`. The separate SQL failure increments it. `BatchFacts::report` then logs one failure, while the controller counts two failed item outcomes. This discrepancy concerns diagnostics and leaves the individual item statuses intact.

**Evidence and disposition.** `src/maintenance/DataRemovalService.cpp:39–62,82–85,110–128`, `src/jobs/JobApplicationsController.cpp:698–728`, `src/logging/LogCatalog.inc:15`, `Requirements/JobTracker_Logging_Events_Updated.md:59–61`. Retain the R0 event behavior. If characterized, compare the item results and log separately using a temporary SQLite fixture.

### F005 — A running CV removal can be logged as a worker-start failure

**Consequence and condition.** Transaction-start/lookup failure for an active CV can occur inside a batch after an earlier item completed. Until eligibility is determined the operation remains `ActiveCvRemoval`. The catch/observation path reports `BackgroundWorkStartFailed` per failed item with count one. The event contract describes an inability to initialize accepted execution/storage.

**Evidence and disposition.** `src/maintenance/DataRemovalService.hpp:54–92`, `src/maintenance/DataRemovalService.cpp:65–71,131–151`, `src/logging/LogCatalog.inc:23`, `Requirements/JobTracker_Logging_Events_Updated.md:91–93`. Keep existing classification and counts. Stage 2 may distinguish lookup failure from genuine worker-start failure in a disposable scenario. No change to log types, aggregation or text belongs to R003/R006.
